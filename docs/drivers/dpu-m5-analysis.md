# DPU M5 panel sleep analysis

**Image gate closed.** y12m refused panel sleep on a false counter-readiness check. y12n passed readiness, completed the two DSI command DMAs on both links, and timed out waiting for the slave INTF's active bit to clear before the driver sent a stop request to the master. Ubuntu v1.4.0 takes a master-first handoff path for this exact shared-CTL topology. The ordering mismatch is established. The y12n capture omits the measurements needed to prove which state the slave was in during the timeout and to validate a handoff that can restore the retained firmware path.

## Sequence comparison

Ubuntu filenames under `msm` refer to `drivers/gpu/drm/msm/` (`disp/dpu1/` for DPU and `dsi/` for the host/manager). The panel is under `drivers/gpu/drm/panel/`. Native line numbers are for the y12n tree at `061fe59c`. Status labels assess each operation in the M5 path.

The observed native path had `piano-dpu-panel=1` with LP DCS and engine stopping enabled. NativeGopDisplay enables the callout for the internal display only (`NativeGopDisplay.cpp:938–939`). The options also allow DCS-only sleep, leaving both timing engines running (`piano-dpu-panel-engines=0`), and high-speed command transfer (`piano-dpu-panel-hs=1`). The worker's normal wake and its undo path both use the same start/flush helper. [Option parsing](../../package/PianoDpu/DpuSlices.cpp#L148-L151)

Ubuntu blanks the panel backlight, drains and stops the DPU, unprepares the panel over the still-powered DSI hosts, and then disables the hosts and PHYs. On enable, the DSI bridge powers the hosts first, the panel prepares and sends its init commands, and the DPU configures and starts the video path. Backlight enable is in the bridge enable phase. Video timing starts at DPU kickoff, after the shared CTL flush.

## Stop evidence and remaining uncertainty

- **Three independent registers.** At INTF base `0x0ae36000` (INTF1) or `0x0ae37000` (INTF2), `+0x000` bit 0 is the timing enable request. This word **does** read back as 1 while scanning on y12n (console 3678 and the awake snapshots). Whether a 0 write is visible there during the failed stop is **unknown**. `+0x26c` bit 0 is the effective active status used by both M5 and Linux on DPU core ≥5, including this DPU 12. Linux uses the enable word as its status source only on earlier cores. `+0x0a8` bits 0 and 1 are the frame/line count enables, separate from both timing words. The raw frame and line counters at `+0x0ac/+0x0b0` advance despite zero count-enable readback. Linux `get_status` returns software zeros for the counts when inactive, so compare actual raw register motion across samples. A good awake sample by itself validates neither stop indicator during disable.
- **The interval spans several frames.** 119.878 Hz gives about 8.342 ms per frame. The 40 ms from the slave enable store is about 4.8 frames. A two-frame bonded latch would take about 16.7 ms. The older Linux slave allowance was a poll *after* the master-side stop, at roughly 1–1.5 ms intervals (40 sleeps at the pin). The pin also has a distinct 40 ms timeout for the CTL handoff flush and an 84 ms master kickoff wait bound. None supports extending Native's slave-only wait. The 20/100 ms waits had already elapsed when the 40 ms window started. Linux's master-drives-slave behavior gives a mechanism for the persistent bit while INTF1 is live. Its patch also records that a slave local request can survive the effective stop until the master route is removed, and that late release after unbinding resources can wedge VBIF halt and the next secondary DSI command DMA.
- **The console narrows the failure to the stop proof.** `KernelIo::wr` returning true means the MMIO word passed the allowlist and map checks and a store and barrier ran. It gives no readback. y12n's timeout is consistent with a slave request that reads 0 while its effective status and counters stay live, a zero write that does not read back/latch, or an active bit that stays set while the counters freeze. A sample across the request is needed to distinguish those. Treat a freeze only as corroboration with clocks still readable and an earlier motion control. It cannot prove the slave request cleared, that the VBIF halt acknowledged or that DSI went idle.
- **DCS completion is local to the host.** `sendDcs` issues DCS short writes with no BTA/panel read and marks success from DMA_DONE on both hosts. It samples DSI_ACK_ERR before and after and stores the FIFO status, but does not use either as an acknowledgment or include them in the transition log. Boot ACK_ERR was zero on both hosts. DMA timing, a zero error latch, backlight darkness and a successful rollback all leave actual panel acceptance of `0x28/0x10` unknown. The stock DT packets also request no ACK. Existing snapshots expose host state only.
- **The current model explains why y12n was a surprise.** `dpu_model.h:162–185,303–338` gives each engine an independent stop latch. `dpu_panel_host.cpp:211–244` tests zero COUNT_EN readback and assumes both stops succeed. Its fault case at lines 288–295 forces a generic stuck slave, exercises recovery and verifies no master stop. A one-off host replay combined y12n's zero COUNT_EN and front-porch DMA path with the existing dropped-store and stuck-engine injections. With INTF2 EN reading 1 in the former and 0 in the latter, both produced the same step-3 timeout, recovery, and ten subsequent gate refusals. Both finished with EN/STATUS reading 1. The model has no shared-CTL route dependence, so the replay demonstrates why the existing log and post-recovery snapshots cannot select between those states.

## Fix-image gate

Path: IOMobileFramebufferLegacy power hook → NativeGopDisplay copy worker → confirmed dual backlight blank and touch hold → PianoDpu worker/flip lock → bonded DCS off → CTL0/INTF stop → wake or rollback → DCS on/PCC/touch/backlight. Ubuntu's counterpart is DRM atomic disable/enable → shared DPU encoder handoff → NT36532 unprepare/prepare with both DSI hosts available → DSI/PHY power sequencing.

Checks: Counter readiness, runtime blank and touch park, bonded command DMA completion and the boot-latched refusal/recovery are evidenced. The shared-CTL stop ordering differs from Ubuntu v1.4.0. Collect the per-link EN and counter history with the trace above. Safe retained-route handoff/restart and panel-side receipt still require evidence.

Root cause: **Closed for y12m. Open for the y12n hardware mechanism.** y12m used COUNT_EN readback as proof of motion and rejected two moving counters. In y12n the standalone slave-idle predicate timed out with the shared master's enable request still in place. Ubuntu's master-first handoff identifies the leading cause at that exact topology. The available y12n measurements cannot distinguish a retained active slave from an unapplied request or stale effective status, and give no evidence that the Linux full-modeset handoff can be reversed safely in the inherited light-sleep path. The M5 image gate stays closed.
